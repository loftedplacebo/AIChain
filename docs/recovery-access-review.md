# Selective restored-access review

Implemented 29 September 2026. This is an **offline dev/test review, access-application and customer-only activation workflow**. Publisher release and hosted staging/production remain gated.

Restoring a backup does not establish current ownership. A backup can contain a removed administrator, an obsolete provider account or a superseded role. Recovery therefore keeps identities disabled, deletes sessions/authentication flows, revokes keys/invitations and leaves the service gate closed.

`prepareAccessReview(pool, {environment, restoreId})` in `services/governance/postgres-recovery.cjs` requires an offline database administrator with full row visibility and database ownership, matching dev/test environment, reviewed migrations, a `gov_restore_` database and its matching pending recovery gate. A local superuser or a database-owning `BYPASSRLS` managed administrator qualifies. It checks that credentials remain invalidated, then reads a repeatable-read snapshot of identity provider bindings, workspaces and memberships. Each inventory is bounded to 10,000 rows; larger restores need a separately designed review procedure rather than silent truncation. Queries have bounded statement/lock waits.

The returned inventory contains personal identity information. Keep it in protected operator tooling; do not log, expose it through the portal/API, or place it in source control. The existing aggregate `reviewRestore` remains suitable for non-personal status reporting. No new HTTP route, CLI credential handling, database grants or automatic file export was introduced.

The SHA-256 snapshot digest binds the database name/OID, environment, restore ID, invalidation timestamp, identities (including provider subject, email, disabled flag and version), workspaces and backed-up memberships. It does **not** bind governance event/evidence contents, worker journals or current provider/network state. It is a stale-state check, not an authentication signature or approval capability.

The operator supplies exactly:

- `snapshotDigest`, copied from the private snapshot;
- `reviewReference`, `providerReviewReference` and `ownershipReviewReference`, referencing independent review records;
- `memberships`, an explicit replacement list of `{workspace, userId, role}`.

`reviewAccessPlan(pool, options, input)` reads the current snapshot again and compiles only if the digest still matches. Unknown identities/workspaces/roles, duplicate memberships, empty selections, missing review references and extra fields fail. Every workspace selected for access requires a selected owner. Workspaces absent from the selection remain suspended in the proposed plan. Unselected backed-up memberships are excluded from the proposed replacement; they are not implicitly preserved. An owner change may be proposed explicitly using an existing identity, without inheriting that identity's old role. Creating a new replacement identity is not implemented.

References are operator assertions, not proof that WorkOS identities are valid, ownership has been independently confirmed or post-backup changes have been reconciled. The returned plan contains IDs/roles and review references, but omits provider subjects/email addresses. It stays `activation: review-required` and `credentials: remain-revoked`. Neither inventory nor compilation changes any data.

## Atomic access application

Migration `012-recovery-access-review.sql` adds the operator-only `governance_recovery_access_reviews` audit table and the `access-reviewed` gate state. `applyAccessReview(pool, options, input)` requires the same offline administrator and matching dev/test restore. It takes exclusive locks on the gate, audit, identities, workspaces, memberships, sessions, authentication flows, keys and invitations, then rereads and recompiles the private snapshot under those locks. A stale review, live credential or changed identity fails before any mutation. Statement timeout is 30 seconds and lock timeout 5 seconds; large selections may need a separately designed operation.

One transaction records the plan and original memberships with database operator/timestamp, replaces memberships with the explicit selection, enables only selected identities while incrementing their versions, and moves the gate to `access-reviewed`. The audit remains outside runtime API/worker grants. Customer administration history, keys, invitations, sessions, events and evidence are not reactivated or rewritten. Workspaces excluded from selection retain their records but no membership. This step is one-use: a second application fails against the changed gate. Failures roll back every change.

`access-reviewed` cannot start or authorize customer repositories or release publishers. Application returns `activation: review-required`, and no public endpoint or CLI activation command is introduced. The coordinated recovery CLI still expects the earlier fully disabled `review-required` phase; after access application use the private audit/gate rather than interpreting that earlier review failure as permission to reopen services.

## Customer-only activation

Migration `014-customer-recovery-activation.sql` adds `customer-active` and an operator-only activation audit. The private functions in `services/governance/customer-recovery-activation.cjs` accept only offline dev/test restores. There is no HTTP route, automatic activation or hosted release permission.

`prepareCustomerActivation(pool, {environment, restoreId, trustedSigners, runtimePool, maxRows?})` requires the offline administrator and a separately connected strict API runtime role. Both connections must identify the same database name/OID; operators must still configure the correct cluster connections. The gate must be `access-reviewed`, with reviewed migrations and the exact restore ID. The complete 21-table snapshot is bounded to 10,000 total rows and 32 MiB of row data, with 30-second statement/review and five-second lock limits. Oversized restores require another designed procedure; no partial review is accepted.

The review binds the database, gate, runtime role, signer policy and every scanned row to a digest. It checks the exact applied membership selection, selected owners and enabled identities; old sessions/flows must be absent, keys/invitations revoked and replay leases cleared. It reconciles event byte/usage/day counters, queue completeness and recording evidence. Signed records require the explicit trusted signer policy and valid commitments/proofs. Unsigned pending records are counted separately and may only be retained unpublished. Submitted hashes remain offline observations, not current Base confirmation.

`activateCustomerAccess(pool, options, input)` requires exactly `snapshotDigest`, `providerReviewReference`, `ownershipReviewReference`, `revocationReviewReference`, `recoveryReviewReference`, `releaseReviewReference` and `unsignedRecords: 'retain-unpublished'`. References are bounded nonsecret operator assertions: this function does not independently certify provider/MFA policy, ownership, missed revocations, external journal reconciliation or release approval. Complete those independent reviews before invoking it for any actual restore.

The transaction locks the gate, activation audit and all reviewed tables exclusively, rereads every check, rejects stale state and revalidates the API role. It atomically inserts the private audit and changes only the service gate to `customer-active`. Failure rolls back both. Old credentials remain revoked; customers require fresh provider sign-in and newly issued keys. Existing evidence, memberships, invitation state and worker journals are not rewritten by activation. Runtime roles cannot read the private audit.

Customer repositories and API readiness accept `customer-active`; unbound evidence-worker readiness, startup and store transactions reject it. Migration 017 adds exact scoped publisher-binding enforcement: only the matching active restore/project/role/identity/policy record can authorize a bound worker store. `GovernanceWorker` checks authorization and its journal release identifier against actual configuration at each tick and immediately before sending. Withdrawal during signing leaves exact signed bytes in the journal without sending. The final check is not an atomic lock across a subsequent external network send. Customer activation alone retains closed SQLite delivery/worker gates. The separate [private coordinated publisher release](restored-worker-journal-review.md#coordinated-publisher-approval-and-revocation) now opens only the reviewed worker journal and scoped PG binding at dev/test scope, with compensation and revocation; delivery journals and hosted release remain gated.

Validation: native recovery run `r1f330edd73ae` passes 24 groups, including observed lock-wait drift, injected audit/gate rollback, repeat denial, fresh session/scoped-read acceptance, old credential denial, strict worker denial and private audit isolation. Native role run `p3d0ed5532e6a` passes seven groups and session run `s68cca24bfb47` passes 25. The worker/recovery suite passes 15 tests, including access withdrawal during signing and exact-byte retry only after authorization is restored. These tests use local synthetic databases/provider observations and perform no Base broadcast.

## Repeated customer recovery

Migration `015-recovery-generations.sql` adds an operator-only lineage table. Fresh-target invalidation now accepts either an original `active` snapshot with no restore identity/time, or an already recovered `customer-active` snapshot with a distinct prior restore ID, valid invalidation timestamp and matching prior access-application/customer-activation audits. These history checks establish internal consistency, not independent authenticity against a database administrator.

Each invalidation inserts a new generation with prior gate/restore/time and operator, then revokes all captured credentials, disables identities and closes the new target to `review-required` in the same transaction. Previous audits and recording evidence remain intact. Migration approval, destination name/OID, same-process fresh handle and source exclusion still apply. An existing restore cannot be reinvalidated in place or passed off as a new destination. A backup of an unfinished `review-required`/`access-reviewed` recovery is still refused by capture/invalidation; use the original authenticated backup in another fresh target instead.

Encrypted captures of `customer-active` databases use the existing quiesced dev/test backup procedure. After restoring, repeat independent provider/ownership/revocation review, selective access application and customer-only activation for the new restore ID. Earlier approval references are not automatic permission for the new generation. Retained SQLite journals still require independent reconciliation; no publisher or delivery release is inferred from lineage.

Native recovery run `r0d2119f81cad` passes 27 groups through migration 015. It encrypts/restores a customer-active database containing a fresh session/key; verifies source access and evidence are unchanged while target credentials are invalidated; applies a second access/activation cycle; verifies a new sign-in, old credential denial, both retained activation audits and publisher denial. Missing prior audit is refused, and an injected credential-write failure rolls back the new generation and credential/gate changes. A repaired fresh handle succeeds once. Strict role run `p4814249ce8da` passes seven groups, including no runtime access to the new audit; two restore-migration approval tests pass.

### Restored webhook-delivery inventory

`recovery-delivery-review.cjs reviewDeliveryJournal({environment,file,bindings,maxJobs?})` now reads the actual `DeliveryJournal` SQLite schema as an offline dev/test operator check. Supply an absolute regular restored file with the matching environment and `review-required` gate, plus an explicit inventory of `{tenant,project,destinationRef,keyRef}` bindings. These are reviewed configuration references only: URLs and signing secrets are neither accepted nor resolved. Duplicate/invalid bindings fail. This is not a customer HTTP endpoint, provider lookup, delivery worker or activation command.

The review reads one transaction across **all** journal scopes. It defaults to 1,000 jobs, permits at most 10,000 jobs and 1,000 bindings, limits the file to 512 MiB and aggregate bodies to 16 MiB, and validates each envelope within 4 KiB. Over-limit scans fail rather than truncate. Envelope identity/scope, destination/key references, state, attempts, clocks, HTTP status and in-flight lease structure must agree. Delivered rows require a recorded successful attempt; that is a structural check of historical local state, not evidence from the receiver. Missing routing bindings are reported separately. The existing signature-envelope validator is reused without generating a signature or acquiring a key.

Output contains only aggregate state/invalid/unmatched-binding counts, scope count and a digest binding the full row snapshot and sorted expected bindings. Bodies, job IDs, tenant/project names, destinations, key references and lease tokens stay out of the report. Valid rows have `journalIntegrity: passed`; any invalid row yields `failed` and routing review `not-checked`. A matching operator inventory establishes references only, not source authenticity, key availability, current ownership or egress permission.

Every result retains `activation: review-required`, `receiverAcknowledgements: not-checked` and `postBackupActivity: not-reconciled`. A restored `sending` job may already have reached its receiver; `pending` may include a lost acknowledgement, `delivered` is historical and `dead` does not justify replay. Reconcile receiver deduplication/acknowledgements, current routing and key policy, related rule/incident/event evidence and post-backup activity before choosing any retry or disposition. Nothing clears a lease, updates a job, changes a gate, sends a request or signs an envelope here. The normal delivery constructor still refuses the restored gate.

Validation: the initial queue review passed 12 delivery/rules/signature tests; the combined command now passes 15 after the rule-link increment below. Queue cases create the real journal and claim/finish jobs into all four states, validate cross-scope/missing-binding and malformed-state handling, refuse a truncated review and wrong/active gates, and compare source bytes before/after review. An actual encrypted rules-journal backup/restore preserves an in-flight job and keeps delivery startup denied. All recovery acceptance data is local and synthetic; the review itself makes no network request or customer delivery.

### Local rule, incident and delivery links

`reviewRuleDeliveryJournal(options)` from the same module adds a full local rule/incident review within the queue reader's **same read transaction**. It requires the actual `RuleEngine` tables; missing tables fail rather than imply no rules. The queue-only `reviewDeliveryJournal` explicitly reports `ruleLinks: not-checked`. Neither entry point changes state or grants activation.

The linked review scans rule definitions, active pointers, processed-event digests, assessments, incidents, lifecycle actions, derived-alert outbox and scan cursors across all scopes. `maxRuleRows` defaults to 1,000 and is capped at 10,000 **in total across those eight tables**, separate from `maxJobs`. Aggregate rule/outbox bodies are limited to 16 MiB, rule/action bodies to 4 KiB and derived alert bodies to 1 MiB. Larger snapshots require another review procedure; no truncated pass is produced. Reports include row counts, mismatch categories and a digest of every reviewed row. The combined digest also binds the queue and operator routing inventory.

Checks include schema-valid historical rule versions and activation ordering; active pointers to the latest local version; assessments linked to their processed digest and exact rule version; deterministic incident IDs and matching severity; complete match-to-incident, incident-to-alert and routed-incident-to-delivery links; validated derived alert scope, policy, monitor, parent reference and original detection time; exact destination/key and deterministic delivery ID; and contiguous lifecycle revisions replayed from open through permitted acknowledge/resolve/reopen transitions. Cursor values are checked structurally. Orphaned, missing and altered links yield `ruleLinks.localLinks: failed`; valid local relationships yield `matched`. Row content, actor identities, scopes, key references and incident IDs are excluded from the aggregate report.

`matched` proves only local consistency. Processed-event digests cannot establish the original event body without comparison to the restored event/evidence store; cursor positions require reconciliation to that store too. Rule artefacts and lifecycle history are not signed merely because they pass these checks. A published derived-outbox label is historical and requires comparison to accepted event/evidence records. Accordingly `eventEvidence`, `cursorAgainstEventStore` and source authenticity remain unchecked/unproven, receiver acknowledgements and post-backup activity remain unresolved, and the service gate stays closed. Retained operational history may legitimately use an older rule version or preserve a now-resolved incident's original open alert; the review validates those original relationships rather than rewriting them to current policy/state.

Validation: `npm run test:governance-recovery-delivery` passes 15 tests. Three added cases use the actual engine and queue: multiple tenant scopes, older/current rule versions, a full acknowledge/resolve/reopen history, unrouted incidents, full-row limit refusal and unchanged source bytes; independent corruption/deletion of rules, pointers, digests, incidents, actions, outbox, routing and cursors; and an actual encrypted restore preserving linked alerts plus an in-flight job while startup remains denied. Existing queue, engine, loopback receiver and signature tests also pass. No provider lookup, Base transaction, external receiver request or activation occurs in the new review cases.

### Rule journal against restored event and recording evidence

`recovery-rule-evidence.cjs reviewRuleEvidence(pool, options)` now compares the linked journal with the restored PostgreSQL event/evidence database. It requires the offline administrator, reviewed migrations, matching dev/test environment, exact restore ID and a `gov_restore_` database gated at `review-required` or `access-reviewed`. Supply the journal/binding options above plus a nonempty explicit `trustedSigners` allowlist. Journal structure, local rule links and routing bindings must pass before the database comparison begins. No runtime role, HTTP route or gate-changing operation is introduced.

The PostgreSQL read-only repeatable-read transaction scans all event scopes in 100-record keyset pages, with `maxRecords` defaulting to 1,000 and capped at 10,000. The event/evidence bodies together must fit 32 MiB; over-limit snapshots fail before loading them. SQL and lock waits are bounded, and comparison has a thirty-second processing deadline. The complete read snapshot is bound to the database identity, restore, signer policy and journal digest. The journal is reread after comparison; drift invalidates the result. Subsequent database or chain changes require another review.

For each processed source event, the comparison requires the original accepted body to match the rule-processing digest, selects the historically applicable rule versions by server receive time and recalculates every assessment, including missing/not-applicable outcomes and assessment-set completeness. For each derived outbox record, its submitted body must match the accepted event, excluding only the server-added `receivedAt`. Referenced source and derived records then pass the existing schema/scope/submission-digest, queue, trusted recording signature, commitment and Merkle-membership verifier. A missing source, mismatched assessment/body, missing published alert or invalid/untrusted evidence yields `recordingEvidence: failed`.

Unsigned referenced evidence, an unpublished derived record, or an accepted derived record still pending in the local outbox yields `incomplete`; the last case needs an acknowledgement-link repair, which is **reported only**. Clean referenced records yield `matched`. Aggregate output reports exactly how many records were evidence-checked and how many scanned records were unreferenced. This is not a claim that every unrelated record was verified; use the independent full-snapshot evidence review for that. No event bodies, scope names, identifiers, actors, signing keys or raw verifier errors are returned.

Positive SQLite scan cursors cannot be mapped implicitly to PostgreSQL event order: they report `sqlite-rowid-mapping-required`, while absent/zero cursors report `not-required`. Scanner migration/reconciliation remains a release requirement. Every result retains `baseVerification: not-checked`, `receiverAcknowledgements: not-checked` and `activation: review-required`. Recording evidence establishes submitted-record integrity, not AI correctness, source authenticity, current chain inclusion, customer ownership, post-backup delivery activity or permission to retry.

Validation: native recovery run `rf08ec2f51df2` passes 23 groups. The new case uses the actual rule engine, accepted source/derived events and real signed batch evidence in the gated restored PostgreSQL database; verifies both referenced records; refuses wrong restore identity, insufficient role and full-scan limits; fails an untrusted signer; reports unsigned evidence incomplete; and rejects a journal change during an observed database read while both service gates stay closed. `npm run test:governance-recovery-delivery` now passes 16 tests; the added comparison case covers missing sources/published alerts, changed bodies/assessments, unsigned/untrusted evidence, uncertain acknowledgements, cursor limitations and deadlines with actual recording signatures. No Base RPC, customer delivery, repair or activation was performed.

## Reviewed older-schema restores

Fresh isolated restore invalidation now accepts optional `approvedMigrations`, an ordered list of shipped `{name, checksum}` entries. It accepts only a known contiguous migration prefix including migration 009 (the original recovery gate). Modified/unknown checksums, gaps/duplicates in applied history, unexpected approval fields and any missing/extra approval fail. A current-schema restore needs no approvals. A pre-012 restore requires approval of every pending migration; the operator must review the actual SQL and compatibility before supplying its checksum. Checksums bind code, not the quality or authority of the review.

The same-process fresh-target handle, destination name/OID, source exclusion, offline administrator, matching dev/test environment and fresh source gate remain mandatory. Under exclusive locks and bounded waits, the transaction applies exactly the approved shipped SQL, records migration history, verifies the complete schema and invalidates all restored access together. Failure rolls back DDL, history and credential changes. No SQL is accepted from configuration, no source schema is migrated, and no existing destination is reused. Even after success, service and journal gates remain closed.

`postgres-backup.cjs restoreBackup` and the existing private `restore` CLI configuration pass through `approvedMigrations`; the successful `recovery.json` marker records the applied names/checksums. There is no automatic approval or production upgrade. The fresh destination has PUBLIC connection permission removed before restore; if approval/invalidation fails, only the offline operator can inspect it under the existing fresh-target rules. Do not expose or grant runtime access to a failed restore.

Two migration-plan unit tests and native run `r9e49fd0d028b` (eighteen recovery groups) validate an actual eleven-migration source dump and fresh restore. Missing/bad approvals, altered history and source targeting fail. An injected invalidation failure rolls back the new audit table and migration 012, retains the old eleven-row history and leaves source access unchanged. Exact approval upgrades the destination and leaves it revoked/disabled with a passing offline recovery review. The legacy case directly exercises native dump/restore and invalidation; it is not an independently generated historical encrypted archive acceptance test. Existing current-schema encrypted/CLI recovery checks also pass.

No synthetic test result authorizes activating an actual restored customer environment. Hosted activation, new identities, off-host custody and production readiness remain open roadmap gates.

## Current provider-binding review

`recovery-provider-review.cjs reviewProviderBindings(pool, options, input, config)` checks selected identities **before** access application. It reads the private disabled-identity snapshot, recompiles the exact reviewed selection, calls the [WorkOS read-only Get User API](https://workos.com/docs/reference/authkit/user), then rereads the private snapshot. Any identity/membership/gate drift during requests invalidates the result. The client ID must match the stored `workos:<clientId>` provider and the subject must be a WorkOS user ID. Server-only API credentials select the provider environment; this lookup does not independently certify that the operator supplied the correct environment key.

Requests use fixed `https://api.workos.com` URLs, GET only, bearer credentials only to that host, redirect rejection, five-second timeout and a 64 KiB response limit. Selection defaults to at most twenty identities, explicitly configurable up to one hundred; total request processing has a thirty-second budget. There are no retries. A provider outage/rate limit stops further requests and reports the remaining identities as unchecked. The adapter uses no sign-in, account mutation, verification email or reset endpoint.

Each selected account must exist, have an exact subject match, the same normalized email as the restored identity, and `email_verified: true`. Results count matched/missing/unverified/binding-mismatch/unsupported-provider/unavailable/unchecked cases without returning personal data, secrets or raw errors. Snapshot and selection digests bind the review to the requested local state. Success is named `providerBindings: matched`, never ownership or account-security approval, and remains `activation: review-required`.

These are point-in-time existence/email checks. They do not prove current workspace ownership, enterprise membership, MFA, suspended-user policy, active sessions, logout history or missed revocations. Those still require independent reconciliation. The function has no automatic API/portal route and no effect on memberships, credentials, gates or provider accounts. It does not itself enforce an approval on `applyAccessReview`; customer-only activation and the separate private publisher release require explicit independent review references as described above. Real recovered-provider and hosted publisher acceptance remain open.

Four unit tests cover matched/missing/changed/unverified accounts, wrong provider realm, malformed/oversized responses, outages/rate limits, bounded selection, unchecked remaining accounts and stale selection. Native recovery run `re43f4e8c55cd` passed twenty-one groups: real restored PG identities remain disabled and services gated; a synthetic lookup can match; a concurrent email change invalidates the review on the final database read. All provider responses in these tests are simulated. Real WorkOS/shared-PG browser and recovered-account acceptance remain open.

## Offline restored-evidence reconciliation

`recovery-evidence-review.cjs reviewEvidence(pool, options)` now checks the full bounded event snapshot in a restored dev/test database. It requires the offline administrator, exact pending restore/environment, reviewed migrations, and an explicit trusted recording-signer allowlist. It works at `review-required` or `access-reviewed`, never at the active/source gate. The read-only repeatable-read transaction uses 100-row keyset pages across all tenant/project scopes. Default limit is 1,000 records, configurable to 10,000; a larger snapshot fails before verification rather than reporting a partial pass. SQL/locks and verification duration are bounded. This operator procedure deliberately bypasses tenant RLS through privileged operator credentials; it is not a customer endpoint.

Every accepted event is schema-validated and compared with its row scope, submission digest (excluding server `receivedAt`) and acceptance timestamp. Missing evidence is acceptable only as explicitly counted unsigned pending work. Stored evidence needs a positive revision and matching stored batch ID; the existing verifier checks recording signature, trusted signer, accepted-record commitment and Merkle membership. Evidence/transaction presence must agree with the pending/batched/submitted queue state. Untrusted signatures, altered evidence, record mismatch and queue mismatch are failures. An unsigned backlog makes the result `offlineIntegrity: incomplete`, even if every signed record verifies.

Output is aggregate counts, a digest of the reviewed event/evidence/outbox snapshot and a digest of the signer policy; it exposes no bodies, identity records, event IDs or raw verifier errors. Results apply to that database snapshot only. It always returns `baseVerification: not-checked` and `activation: review-required`. An offline submitted transaction hash is not proof of canonical inclusion, confirmation or finality. Pending unsigned content has no recording signature; an administrator able to replace its body and recompute the submission digest cannot be detected by this check. Source authenticity and AI correctness remain separate claims. This routine does not reconcile publisher/delivery journals, provider identities, aggregate usage or orphaned storage; those have separate review requirements.

One real-signature unit test and native run `r6b819aa9de1e` (twenty recovery groups) verify signed receipt/proof checks, altered signatures, wrong trust policy and queue mismatch without writes/activation. The native scan crosses the page boundary with 102 records across two tenant/project scopes, reports 101 unsigned pending records, detects a changed digest on the final pending record and refuses a one-record limit. Existing source exclusion, access rollback, migration upgrade and encrypted recovery groups also pass. No Base RPC was called or transaction published by these tests.
