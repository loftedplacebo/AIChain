# Restored worker journal review

## Disposable Base index cache review

The deployed Base indexer currently persists **JSON**, not a SQLite index journal. The existing encrypted SQLite journal archive's generic `indexer` role does not capture or validate that JSON format. Do not point a SQLite archive entry at the JSON file or treat its role label as proof of index coverage. The cache is derived from public chain events: the preferred recovery action is a fresh index rebuilt from the reviewed contract/deployment start. Backup custody of customer evidence and operational journals remains separate.

`recovery-index-review.cjs reviewIndexSnapshot(options)` adds an operator-only read check of the actual JSON format. Supply an absolute regular file, dev/test operator context, the exact reviewed `startBlock`, a read-only provider and expected contract `codeHash`. The file itself has chain/contract/start binding, but no persisted dev/test marker; the environment argument is operator context, not evidence of environment isolation. This first review supports the deployed Base Sepolia **batch-only** contract. Individual/authorised or multi-contract caches need another review policy and are refused rather than silently omitted.

The file is limited to 16 MiB. `maxEntries` and `maxCheckpoints` default to 1,000 and cap at 10,000; `maxLogs` defaults to/caps at 10,000. Checkpoints must cover a contiguous prefix from the selected start, each range at most 1,000 blocks, ending at the stored cursor. Legacy/unbound caches, malformed positions and over-limit snapshots fail. Review never writes, rewinds, replaces or activates the cache.

The provider is used only for network, block number/hash, contract code and bounded range-log reads. Observations have a configurable maximum five-second timeout and thirty-second overall processing bound; configure transport timeouts as well because timing out a promise does not cancel the underlying provider. It pins the current observation head and checks the expected code at that numbered block. Every stored checkpoint must still be canonical before and after its log scan. Logs must match contract/range, valid block/transaction/log positions and canonical event-block hashes; duplicate positions, removed logs and malformed known batch events fail. Replaying those logs with the indexer's existing parser builds the expected maps, including publisher-scoped V2 IDs and historical overwrite semantics. Stored batch maps must match the replay exactly.

Final checks reread the pinned observation block and source file; chain or file drift invalidates the result. Aggregate output includes cache match/failure, checkpoint/log/anchor counts, indexed boundary, lag, confirmation-policy status and digests binding the source, replayed map, observed head, code and policy. It excludes batch IDs, publishers, transaction hashes and payloads. Attached manifests are counted as **not verified** here; their receipt commitments/signatures and evidence-store links require separate verification. RPC observations are not independent proof of provider truth or AI correctness.

The confirmation default is twelve blocks after the last indexed checkpoint. `pending` means insufficient depth; `matched` means only that the cached prefix agrees with this observation, **not** that it is current. Lag may be substantial even when all comparisons match. An empty prefix remains pending. Every result retains `activation: review-required`; this is a report, not a startup gate or permission to restart an existing daemon. No backup format, running index, service restart or hosted release was changed.

Validation: `npm run test:governance-recovery-index` passes 13 tests: three new review cases plus existing indexer/launcher regressions. New cases use a JSON file produced by the real `syncIndex`, preserve its exact bytes, replay logs through synthetic read-only provider responses and verify lag/depth. They detect checkpoint reorgs, altered/missing anchors, wrong network/code/configuration, malformed/duplicate/out-of-range data, incomplete bounded history, changed tip/file and stalled requests. No live Base RPC, publication or customer service activation occurred.

Implemented 29 September 2026 as an offline dev/test operator check. Worker startup, rebroadcast and other recovery activation remain gated.

`services/governance/recovery-worker-review.cjs reviewWorkerJournal` accepts an absolute regular restored SQLite journal path, matching dev/test environment and operator-supplied expected tenant/project/publisher/recorder identity. It opens SQLite read-only, reads a single transaction snapshot and requires the restored `review-required` gate. The backed-up config must match that expected identity, Base Sepolia chain 84532 and the current governance anchor contract. The check supports the actual `GovernanceWorker` `config`/`jobs` schema; generic or legacy journals without that configuration fail rather than receive an implicit approval.

The review defaults to 1,000 jobs with an explicit maximum of 10,000. Files over 512 MiB, aggregate job bodies over 16 MiB and configuration bodies over 4 KiB fail before loading jobs. Individual bodies have a 1 MiB parsing bound; signed raw transactions have a 64 KiB encoded-data bound. Oversized snapshots do not produce a partial pass. No service or wallet is started, and no provider is constructed.

Each signed transaction must have a valid signature, matching recorded hash and nonce, expected publisher, type 2, chain 84532, zero value, expected contract, positive gas/fee values and the `anchorBatch` calldata. Batch root/publisher must derive the journal job's batch ID, the leaf count must be 1–1,000 and the receipt schema must match the current implementation. Distinct signed jobs sharing a nonce are flagged as conflicts. Unknown states or inconsistent job IDs are invalid. Prepared unsigned jobs and external transaction references are counted separately; references without raw signed bytes cannot be validated as local transactions.

The report contains aggregate counts and a digest binding expected configuration and all job rows. It returns no signed bytes, IDs, raw error messages or destinations. `journalIntegrity: passed` means only that this snapshot's configuration and transaction structure/signatures passed. It always returns `networkReconciliation: not-checked` and `activation: review-required`. Historical confirmed/submitted labels are not current inclusion evidence. This result is neither a spend-policy review nor an approval to send a transaction.

Before releasing a publisher, independently compare jobs to restored PG batch evidence and current canonical chain receipts, reconcile publisher nonces and post-backup activity, verify current runtime code and current gas/spend policy, and decide how uncertain or external jobs must be handled. Restore-era delivery/webhook jobs and derived index state need their separate reviews described here and in the access-review procedure. The older capped relayer is a separate JSON prototype, not this SQLite publisher journal; inventory any installation of it independently. This module does not update, delete or mark jobs completed, change gates, retry deliveries, broadcast, replace nonces or spend gas. There is no HTTP or automatic CLI activation interface.

Validation: a real signer creates two distinct Base Sepolia anchor transactions with the same nonce. The test verifies signed bytes, altered hashes/nonces/publisher rejection, conflicting nonce detection, full-review limits, environment mismatch and unchanged source database bytes. The actual encrypted SQLite backup/restore path preserves a signed worker job and its review digest while retaining the gate. Historical `confirmed` still leaves network reconciliation unchecked. The new review test plus four existing worker tests pass (five total); existing tests cover uncertain-broadcast restart, exact-byte retry, commit interruption, concurrency, policy gates, RPC outage and reorganisation behavior. These are local synthetic tests; no chain transaction or customer webhook is sent.

## Comparing worker jobs to restored PostgreSQL evidence

`recovery-worker-evidence.cjs reviewWorkerEvidence` combines the gated worker snapshot with read-only, repeatable-read evidence from the matching restored dev/test PostgreSQL database. It requires the offline database superuser, reviewed migrations and exact restore/environment. The scope is one operator-selected tenant/project/publisher/recorder; it is not a claim that every tenant or worker has been reviewed. Defaults are 1,000 jobs and 1,000 evidence records, with explicit maximum 10,000 for each; over-limit snapshots fail rather than truncate.

For each journal job, the comparison requires the complete stored batch, matching publisher/root/schema/leaf count and every event's valid trusted recording signature, accepted-event commitment and Merkle membership. Signed calldata must match that evidence batch's root/count/schema, not just derive its ID. The check reports missing worker jobs for the expected publisher and separately counts batches belonging to other publishers. Conflicting recorded transaction history is a divergence. A journal transaction absent from database evidence is reported as requiring a link repair; nothing is changed automatically.

Without an RPC provider, a historical confirmed job returns `submitted-offline`; unsigned work returns `prepared`. An explicitly supplied read-only provider uses the existing Base verifier for runtime fingerprint, expected publisher-scoped anchor event, canonical block and confirmation policy. Reports count confirmed, confirming, reorg, not-found, unavailable or failure states separately. `rpc-checks-enabled` describes configuration, not a successful network check or finality guarantee; inspect state counts. The module exposes no broadcast or signing method. Each RPC observation is limited to five seconds and the review has a thirty-second budget; timed-out observations may finish in the underlying read-only transport, so operators must also configure provider transport timeouts. There are no retries.

The worker snapshot is reread after verification, and journal changes invalidate the result. The PostgreSQL data remains a stable historical snapshot during the read transaction; subsequent database or chain changes require another review. The report binds both snapshots with a digest and exposes aggregate counts only. It always retains `activation: review-required`. Publisher nonce state, activity after the backup, independent customer ownership, repair application and rules/indexer/relayer reconciliation remain outstanding; this report is not a final release decision.

Validation: the combined native recovery run `r94946f8d4187` passed twenty-two groups. A real signed worker transaction matches a restored PG batch, a missing job is counted, simulated canonical RPC inclusion produces confirmed observations, and a worker change during the RPC lookup causes rejection while both gates stay closed. The comparison test verifies all three receipt signatures, incomplete batches, transaction divergence, missing-link reporting, simulated confirmation, reorg and outage. The signed-journal encrypted round-trip test also passes. These checks do not constitute a live network restore acceptance test.

## Combined publisher readiness

`recovery-publisher-readiness.cjs reviewPublisherReadiness(pool, options)` combines the existing signed-journal, scoped PostgreSQL evidence, canonical receipt, publisher nonce and proposed spend-policy reviews. Supply the worker identity/file/environment/restore ID and bounded job/record limits, the five-field spend policy, optional observation clock/confirmation threshold, an explicit reviewed contract `codeHash`, and a read-only provider. Only network/code/receipt/block/nonce reads are called; no signer, key, broadcast or gate-changing interface is used.

The evidence reviewer now also accepts a `customer-active` restore, allowing independent publisher reconciliation after customer access has reopened. Its digest includes the gate, and scoped event/bundle bodies are capped at 32 MiB before loading. The original pending restore states remain supported; an ordinary active source or the wrong restore still fails. All database review requires the offline superuser, reviewed migrations and the matching dev/test `gov_restore_` database.

The combined report checks the Base Sepolia contract fingerprint explicitly, requires one unchanged journal digest across the spend/nonce observations, rereads the PostgreSQL evidence/gate snapshot after network observations, rereads the journal and rechecks the nonce observation block before returning. Each RPC has a five-second cap and the overall sequence a 90-second budget, with existing bounded SQL waits. Configure underlying transport timeouts too: an observation timeout cannot cancel an already issued read. These drift checks do not create an atomic snapshot across PostgreSQL, SQLite and the external network.

Aggregate blockers identify external references, publisher batches absent from the journal, missing transaction links, unresolved canonical signed evidence, incompatible current spend policy and unexplained/pending nonce activity. Signed jobs must be canonically confirmed and below the observed confirmed nonce; pending/confirmed account counts must agree. Valid unsigned prepared batches are counted, not signed or sent. Other publishers remain explicitly outside this scoped review.

No blockers yields `ready-for-independent-release-review`, never permission to publish. Every result retains `activation: review-required`, `actualFees: not-reconciled`, `postBackupActivity: not-enumerated` and custody/ownership/other-publisher limitations. Independent account activity, actual fees, signer custody, owner/provider policy, other journals and operational approval still need review. The report binds its component digests and policy/fingerprint without exposing identities, hashes or signed bytes. It neither repairs links nor changes reservations, jobs, credentials or either recovery gate. A separate reviewed publisher-release transition remains unimplemented.

## Scoped publisher runtime bindings

Migration `017-scoped-publisher-releases.sql` adds a forced-RLS runtime binding registry and an operator-only review table. The registry admits `prepared`, `active` and `revoked` records. A composite foreign key requires the matching private review/restore identity; unique partial indexes prohibit two active records for the same publisher wallet or project within one database. The strict worker role receives scoped SELECT only; API roles have no access and neither runtime role can approve, revoke or read private review contents.

The runtime enforcement is separate from the [private coordinated approval procedure](#coordinated-publisher-approval-and-revocation). A PostgreSQL evidence-worker store may be constructed with the exact reviewed `{tenant,project,releaseId,publisher,recorder,policyDigest,codeHash}` binding. At `customer-active`, startup and every store transaction require the exact current restore, project scope, runtime database role and active matching metadata. Unbound, prepared, revoked, wrong-role or foreign-project work remains denied. API/customer readiness remains independent; the generic unbound worker readiness probe still refuses customer-only activation.

`GovernanceWorker` reads an optional private `governance_publisher_release` journal record and compares its release identifier with the actual scope, gas signer, recording signer, runtime fingerprint and normalized five-field spend-policy digest at tick entry and immediately before send. Missing or changed metadata/policy refuses a bound restored worker before work/sending. Policy fields exclude the pause flag; normal paused behavior still applies. This is a trusted-runtime configuration binding, not proof that independent custody/account/fee reviews happened or a distributed process lease. Copying an approved journal and wallet across hosts still requires independent singleton/custody controls.

Fresh restore invalidation revokes every captured registry record atomically with customer credential invalidation, retains the private review and leaves the new PG/journal gates closed. The original source registry remains unchanged. Knowledge of a release identifier does not change any approval state; all writes are offline operator actions.

The worker launcher now opens an existing journal read-only before constructing an RPC provider. A restored journal must have an approved gate, matching environment (when marked), PostgreSQL storage and exactly one bounded full seven-field binding. It compares this binding with actual wallet addresses, scope, the shared normalized worker policy and the runtime contract fingerprint, then supplies it to the strict PostgreSQL worker store for database authorization. There is no environment-variable approval override. Missing new journals and original journals without recovery/release metadata retain the existing unbound path, which still cannot pass a customer-active PostgreSQL gate. The worker's lock and tick/pre-send checks remain necessary after this startup read; it is not an atomic approval or a distributed lease.

Five launcher-binding tests cover matching read-only loading, configuration drift, closed/missing/oversized/duplicate metadata, environment/storage/orphan approval refusal and the original startup path. They use local SQLite fixtures and no network. The worker/recovery suite now passes 27 tests, including reviewed nonce checkpoint and read-only RPC transport checks. Native registry acceptance and coordinated release acceptance have separate evidence; no live publisher run is claimed here.

The private review/activation coordinator, scoped revocation and private-file operator commands are now implemented at dev/test scope below. Hosted operational acceptance remains open. Do not create release records manually as a substitute for independent reconciliation. No real publisher, wallet, VPS process or hosted service was activated by this development stage.

## Coordinated publisher approval and revocation

`publisher-recovery-release.cjs` is a private operator API, with no HTTP route or implicit permission to restart a service. It supports only dev/test, a `gov_restore_` database at `customer-active`, a strict non-owner evidence-worker connection to the same database name/OID and a stopped restored SQLite worker journal at `review-required`. Name/OID comparison is a connection-consistency check, not cryptographic identification of a cluster; operators must use reviewed connection configuration. The separate SQLite delivery/rules journals remain closed.

Call `preparePublisherRelease(pool, options)` with the existing publisher readiness options and `runtimePool`. All local evidence, saved spend state and current canonical receipts/nonces must reconcile. It returns a private full binding, worker role, exact restore/environment, snapshot/review digests, nonce checkpoint and review time. The five-minute plan lifetime is an upper bound, not a promise that changed chain/account/evidence state will remain admissible. Account activity, actual fees, custody, ownership, provider policy and other publishers still require independent reviews; the local report cannot supply them.

Call `activatePublisherRelease(pool, options, input)` only after stopping the worker and completing those reviews. Input must contain exactly `plan`, `quiesced: true`, `providerReviewReference`, `ownershipReviewReference`, `accountActivityReviewReference`, `actualFeesReviewReference`, `custodyReviewReference`, `otherPublishersReviewReference` and `releaseReviewReference`. References are bounded offline operator assertions, **not verified external proof**. The coordinator takes the existing never-age-reclaimed journal owner lock, a SQLite immediate transaction and PostgreSQL gate/registry/audit and evidence write-exclusion locks. It rereads the readiness report after lock acquisition, verifies the plan again and independently checks current-time spend compatibility. The reviewed spend clock is pinned for digest comparison. Its nonce checkpoint is rechecked canonically while the current pending nonce still has to match; harmless head advancement does not itself stale the plan, but a reorg, head regression or account activity can block it.

The private audit and scoped active registry state remain in an uncommitted PostgreSQL transaction while the complete journal binding and `approved` SQLite gate commit. Only then does PostgreSQL commit, and the owner lock stays held until completion. An earlier database constraint/trigger error rolls both pending changes back. If the PG commit fails or its result is uncertain, compensation closes the journal gate, removes local release metadata and attempts an audited PostgreSQL revocation. Any failed compensation retains the owner lock for manual reconciliation. Signed bytes, job states, nonces, reservations, evidence, customer credentials and the customer gate are never reset by this operation.

There is no cross-database atomic commit: a process crash may leave the journal approved while the PG transaction did not commit, or both committed with the owner lock still present. Treat every retained lock/uncertain result as a stopped-owner reconciliation task; do not reclaim the lock by age or blindly rerun activation. Inspect both stores with private operator access, reconcile the exact release ID, use scoped revocation if needed, and only remove a lock after independently confirming its owner is stopped. A new review is required before retrying. Copying approved files/keys to another host is outside the single-host owner-lock guarantee.

`revokePublisherRelease(pool, {environment,restoreId,releaseId,tenant,project,reviewReference})` requires the offline administrator and exact current restore/project record. It atomically records private revocation audit and marks the registry revoked; repeats are idempotent. The local journal and its signed work remain untouched. Bound workers then refuse at the next authorization check even if the SQLite gate still reads approved. An already in-flight external send cannot be atomically recalled by database revocation.

Native acceptance uses real PostgreSQL/SQLite stores with synthetic chain observations and explicit synthetic review references. It covers actual lock-wait evidence drift, stale policy, missing quiescence, existing owner locks, rejection before journal commit, a committed PG transaction with lost response, failed compensation retaining its lock, matching launcher/runtime admission and exact scoped/admin-only revocation. No real wallet, VPS or hosted customer service is activated; see [native validation](governance-postgres-native-validation.md).

### Private-file operator commands

`node scripts/governance-publisher-recovery.cjs prepare|activate|revoke ABSOLUTE_PRIVATE_CONFIG_FILE` exposes the private workflow without a wallet or signer. Hosted stages are refused. Argument lists contain only the operation and config-file path. Keep actual configuration, connections, RPC URLs, plans and references in an ignored operator directory protected for the current operator. Unix inputs must be regular non-symlink files without group/other permissions. Windows input ACLs must be established independently; POSIX mode bits do not verify those ACLs. Newly generated plan directories use the existing private-directory helper, including current-user Windows ACLs.

Start from [the prepare configuration template](../deploy/governance/publisher-recovery.example.json), replacing every placeholder with independently reviewed values. Both connection files contain exactly `{"url":"postgresql://USER:PASSWORD@HOST/DATABASE"}` and optionally an absolute `caFile`. They identify the offline administrator and strict evidence-worker role separately. The existing connection parser requires verified TLS outside loopback. The RPC file contains exactly `{"url":"https://REVIEWED_RPC_ENDPOINT"}`; any API token remains in that private file. No private recording/gas key is needed by any of these commands.

The default RPC adapter exposes only network, code, receipt, head/block and nonce reads. Its HTTPS transport pins the configured URL, verifies certificates, rejects redirects and all non-200 responses, has no transport/startup retries, limits requests to 32 KiB and responses to 1 MiB, and uses a five-second transport deadline. Its RPC allowlist excludes signing, submission and wallet/account methods. Network identity is read explicitly from `eth_chainId`; the adapter does not trust its configured formatting network as an actual chain observation. Tests may inject a synthetic provider in process, but there is no file/environment option to bypass HTTPS, certificate validation or read-only methods.

1. Complete the independent reviews and stop/quiesce the worker before preparing. Run `prepare` with the private template-derived config. The command creates a fresh protected `plan.json`; stdout reports its path, environment, restore/release ID and `activation: review-required`, without wallets, connection strings, RPC URLs or signed work.
2. Create a private review JSON containing exactly the complete generated `plan`, `quiesced: true` and all seven review references listed above. Do not invent references or treat a prepared report as independent approval. For `activate`, use the same options as prepare, remove `outputRoot`, and add the absolute `reviewFile` path. A plan must still be within five minutes and match the reread state. Successful activation opens the scoped binding and journal only; it does not start a worker, fund a wallet, sign or send a transaction.
3. For `revoke`, use a separate private config containing exactly `environment`, `connectionFile`, `restoreId`, `releaseId`, `tenant`, `project` and `reviewReference`. It needs no worker connection, journal file or RPC access. The offline administrator must match the current recovered database. It revokes only the exact binding and retains signed journal work.
4. If any command fails, inspect both stores privately. The CLI suppresses raw errors/credentials and returns a nonzero exit. `manualReconciliationRequired: true` identifies a retained owner lock after failed compensation; a false value is not proof that all other operational checks passed. Never clear locks by age or rerun activation blindly after an uncertain result. Normal Node runtime warnings may also appear on stderr.

## Current publisher nonce observations

`recovery-worker-nonces.cjs reviewWorkerNonces` accepts the same restored worker path, dev/test environment, expected identity and bounded job policy, plus an explicitly supplied read-only provider. Journal integrity must pass before the first provider call. The provider interface uses only `getNetwork`, `getBlock` and `getTransactionCount`; no wallet, broadcast, signing, replacement or gate-changing method is used.

The review requires Base Sepolia, pins the confirmed account nonce to a numbered latest block, then reads the pending nonce and rechecks the pinned block's canonical hash. Invalid counts, a pending count below the pinned confirmed count, unavailable blocks, changed hashes, RPC failures and journal drift invalidate the report. Each observation has a five-second maximum (configurable downward) and the whole review has a thirty-second bound, with no retries. Configure transport timeouts too: timing out a promise cannot cancel an underlying read-only RPC request.

The aggregate report separates signed jobs into:

- `consumed`: nonce below the confirmed nonce at the pinned block. This does **not** establish that the recorded job consumed it; independently verify that job's receipt and evidence.
- `pendingOrAdvanced`: nonce between the pinned confirmed count and observed pending count. The provider may be observing a pending transaction or newer mined activity; transaction identity remains unresolved.
- `atObservedPendingNonce`: equals the observed pending count. This is an observation, not a reservation or authorization to publish.
- `future`: above the pending count. Dependencies and gaps require operator reconciliation.

Unsigned jobs and external hash references remain separate unresolved counts. The report includes the block/nonce observation, timestamp, worker snapshot digest and combined observation digest, but no transaction hashes, signed bytes or publisher address. It always returns `activation: review-required` and `postBackupActivity: not-enumerated`. Account nonces do not enumerate post-backup transactions or complete a publisher audit. Mempool views vary by provider and can change immediately; repeat the review before any approved activation and reconcile canonical receipts, evidence, all publishers and uncertain journals separately.

## Current-policy spend review

`recovery-worker-spend.cjs reviewWorkerSpend(options)` adds an offline dev/test review of the **active `GovernanceWorker` SQLite journal**. Supply the existing file/environment/expected identity/full-job limit, an observation `now` (default current clock), and exactly `{batchSize,maxTransactionsPerHour,maxGasPriceWei,dailyReservationWei,l1AllowanceWei}` as the proposed policy. Integer limits and positive decimal wei values are bounded. No signer, provider or live account is required. Signed-byte/identity integrity must pass first; the review uses the same single read snapshot and never modifies it.

For each signed job, execution ceiling is calculated from actual transaction `gasLimit × maxFeePerGas`. Adding the proposed L1 allowance gives the current conservative reservation requirement. Stored reservations must be valid positive decimal values and at least that requirement. The review flags transactions above the proposed fee/batch caps, missing or future signing timestamps, rolling-hour counts above the policy and rolling-day stored/required reservation sums above budget. It includes historical confirmed jobs because local labels alone cannot establish whether a replay liability still exists; independently reconcile canonical receipts before deciding their disposition. Unsigned and external-reference jobs are counted separately and are not treated as fee-accounted signed work.

Reports expose aggregate counts and decimal wei totals, plus digests binding the journal, observation time and exact policy. They omit identities, transaction hashes and signed bytes. A conflict returns `spendReview: requires-reconciliation`; an arithmetically compatible snapshot returns `compatible-with-recorded-state`. This is not actual-fee accounting or release permission. Stored signing timestamps are not authenticated by Ethereum transaction signatures, later/external activity is not enumerated, and Base L1 allowance is **not** a protocol-enforced total fee cap. Every report retains `activation: review-required`; no reservation is reset, transaction replaced, key accessed or broadcast attempted. Release still needs current chain/nonces, evidence, actual fees, custody and operator review.

## Publisher inventory: older capped-relayer prototype

The product's launcher uses `services/governance/worker.cjs`: it persists signed bytes, nonce, reserve and signing time in a scope/signer-bound SQLite journal before sending. `services/relayer/base-sepolia-capped-relayer.js` is an earlier synthetic prototype that persists a **JSON budget ledger** containing reservations, statuses and sometimes transaction hashes, but no signed bytes or nonces. Repository references to that class currently occur only in its tests. It is not a required second product publisher, and a SQLite archive entry labelled `relayer` does not cover its JSON state.

Do not infer that an older hosted installation is absent from a repository search. Deployment inventory must identify every actual signer/wallet/ledger. If the prototype was ever operated, preserve its budget JSON and independently reconcile its transaction hashes and uncertain reservations against account activity; do not import it as a worker journal, reset its budget or run it alongside the product worker on the same wallet. Its replacement/shared-lock and total-fee limitations remain documented in the prototype runbook. This audit changes neither the prototype code nor any live service, wallet or archive.
