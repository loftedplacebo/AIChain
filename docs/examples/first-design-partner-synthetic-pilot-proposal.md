Internal working draft, 5 October 2026. No partner has agreed this scope.
Do not send it as a contract or promise a service level. A provisional,
supervised API smoke test may begin after Stage A below; the full evidence
trial requires the later start decision.

The proposed application emits **three content-free records** using
[`design-partner-synthetic-set.py`](../../examples/design-partner-synthetic-set.py):
one completed normal run, one unresolved run, and an alert related to that
unresolved run. It uses invented references and no real request, customer,
prompt, conversation or document content.

## Permitted synthetic fields

Only the fixed manifest fields generated by the rehearsal script are in scope:

| Group | Supplied synthetic fields |
| --- | --- |
| Scope and identity | `schema`, `schemaVersion`, `profile`, `tenantRef`, `projectRef`, `environment`, `eventId`, `streamRef`, `sequence` |
| Time and source | `occurredAt`, `receivedAt`, `eventType`, `source.kind`, `source.integrationVersion`, `source.keyRef` |
| Agent/run references | `agentRef`, `runRef`, `caseRef` where applicable, `parentEventRefs` for the alert |
| Model/run description | `model.providerRef`, `model.modelRef`, `model.deploymentRef`, `model.configVersion`, `activity.taskClass`, `activity.latencyMs` |
| Synthetic result or alert | `result.status`, optional `result.predictedLabel`, and for the alert `monitor.monitorRef`, `signalCode`, `severity`, `disposition` |

Omit names, email addresses, customer or employee IDs, prompts, responses,
source documents, raw logs, credentials, health data and production decisions.
The partner must approve the exact field list before integration. Any field
addition requires review rather than silently expanding the pilot payload.

## Provisional partner onboarding checklist

The first contact can receive the [draft event JSON schema](../../spec/governance/governance-event-v0.1.0-draft.schema.json)
and [three-record example client](../../examples/design-partner-synthetic-set.py)
before any account or key is created. The current HTTPS ingestion route is
`POST https://api.orvessian.com/v1/events`; it accepts a project-scoped
Bearer key and a bounded JSON event. An HTTP 201 means the event was accepted,
not that evidence was signed or anchored.

### Stage A — one-day, supervised API smoke test

- [ ] Identify the partner technical contact and Michael's agreed test window.
- [ ] Agree a synthetic-only field allowlist and explicitly exclude real user
  content, personal data, prompts, responses, documents and production traffic.
  Review the short trial terms, privacy/contact route and any partner security
  requirements before credentials are shared.
- [ ] Create a separate partner workspace and project. Admit named test users
  through the existing approval rule and verify MFA and project isolation.
  Have Orvessian first run an internal one-record submit/read-back test in that
  exact new project and confirm the operator project cannot read its record.
- [ ] Confirm the new project's database rows are in the existing encrypted
  PostgreSQL backup scope. Record a manual check plan for its ingestion and
  pending evidence; the automated evidence-backlog alert still covers only
  Synthetic Validation.
- [ ] Issue a short-lived **write-only** project key for this test, transmit it
  through an agreed secure channel and record its owner/expiry. Never reuse the
  operator's Synthetic Validation key or send a secret in ordinary chat/email.
- [ ] Partner submits one fixed synthetic event to `/v1/events`; confirm its
  ID and HTTP 201, then read it back with a separate read-scoped key or an
  authorised portal session. Retry the exact same ID and payload to verify
  duplicate handling. Record that signed evidence may remain pending.
- [ ] Revoke the disposable write key after the test and confirm a repeat
  request is rejected. Decide together whether to proceed to Stage B.

### Stage B — supervised evidence trial

- [ ] Agree partner reviewers, dates, support window, backup owner, escalation,
  pause/exit procedure and success measures below.
- [ ] Deploy and review a separate instance of the existing evidence-worker
  code bound to the partner project, with a distinct journal and protected key
  custody. Extend the coordinated backup to pause that worker and capture its
  journal; download and review a restore of the expanded backup.
- [ ] Extend automated evidence-backlog monitoring to the partner project and
  confirm an alert has a named recipient. Rehearse the pause procedure for the
  agreed trial scope.
- [ ] Issue scoped trial keys with agreed expiry. Submit the three fixed
  synthetic records, reconcile portal/API views, and independently verify at
  least one signed export and Base Sepolia anchor. Record observed results and
  deviations against the agreed measures.
- [ ] Revoke trial keys, review data retention/deletion and exports, and record
  the partner's continuation decision at the end of the trial.

Stage A is deliberately limited to ingestion and read-back. If a partner needs
signed evidence in its first test, complete the Stage B worker, backup and
monitoring work before issuing the key.

## Trial steps and proposed acceptance measures

These are proposed targets for the partner discussion, not an availability
promise. Record timestamps and evidence IDs during the trial.

| Measure | Proposed target | Observed result |
| --- | --- | --- |
| Access to first accepted synthetic record | Within one supervised business day | Pending |
| Fixed set accepted and replay-safe | 3 of 3 accepted; retry of identical set creates no extra records | Pending |
| Portal reconciliation | Reviewer finds all 3 IDs and distinguishes normal, unresolved and alert states | Pending |
| Signed evidence | At least 1 eligible export passes the independent verifier against the trusted recording signer and Base Sepolia anchor | Pending |
| Evidence delay labeling | Any pending or failed anchor is shown as pending/failed, never as verified | Pending |
| Reviewer usefulness | Partner reviewer can explain the selected decision and identify the investigation next step in a supervised 15-minute review | Pending |
| Key retirement | Revoked submission key receives HTTP 401 for a new request | Pending |
| Partner judgment | Technical contact and reviewer record whether this workflow is worth a second trial | Pending |

An API HTTP 201 is an ingestion acknowledgement. Signed receipt and Base
verification are separate evidence checks; Base Sepolia is testnet only.

## Access, support and pause

- Create a **separate partner workspace/project**, named users, a short-lived
  submission key and a separate read-only verification key. Do not share the
  operator's Synthetic Validation project or key.
- Before a partner evidence trial, bind a reviewed instance of the existing
  evidence worker to that project, include its journal and database records in
  encrypted backup/recovery scope, and extend backlog monitoring to that
  project. The current hosted worker and monitoring cover Synthetic Validation
  only. Stage A above permits a bounded ingestion-only smoke test first.
- Michael Grant is the current Orvessian incident and support owner. Agree a
  backup person, partner escalation contact, support hours, response target,
  notification channel and the partner's right to request a pause before
  start. Until then, no support SLA is represented.
- For emergency containment the pilot owner can stop the hosted API as in the
  [support runbook](../pilot-support-and-incident-runbook.md). That also
  interrupts portal reads. The partner should retain original event IDs for
  safe retry. Agree the deletion/return and exit process before any record is
  accepted.
