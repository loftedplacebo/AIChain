## Read-only baseline

The B2 completion marker covered the 03:00 UTC due backup. A restricted pilot
API connection read a point-in-time cluster snapshot at 07:56:23 UTC:

- `max_connections=50`, `superuser_reserved_connections=3`;
- `governance_test` had 5 active connections and used 10,737,331 bytes;
- `governance_prod` did not yet appear in database statistics;
- no combined-load throughput, CPU, memory, disk I/O or latency result exists.

This is not a usable production connection budget. The existing cluster is a
2 GiB RAM, 30 GiB storage, single-node service. Obtain DigitalOcean managed
database metrics over a representative pilot window, then measure both workloads
together on the proposed production plan before opening traffic. Bound API and
worker pools so peak ordinary connections plus operator and backup allowance
stay below the 47 non-reserved connection slots. Set measured warning and stop
thresholds for connections, CPU, memory, storage, latency and evidence backlog.

## Reviewed database sequence

1. Record provider cluster ID, region/VPC, plan, admin ownership, maintenance
   window, current automated recovery status and pilot backup completion marker.
   Verify the pilot remains healthy immediately before the change.
2. Create only the distinct `governance_prod` database and three login roles
   `governance_prod_migrations`, `governance_prod_api` and
   `governance_prod_worker` in DigitalOcean. Generate separate credentials in
   protected storage. Do not reuse pilot passwords or put `doadmin` in a service.
3. Connect as cluster administrator to **`governance_prod`**, verify
   `current_database()`, and apply `01-bootstrap.sql`. Review role memberships
   and confirm no runtime identity inherits an owner or administrator role.
4. Connect as `governance_prod_migrations` to `governance_prod`, set
   `GOVERNANCE_ENV=prod` and apply the reviewed migrations. The runner now
   rejects a different database or migration role before changing schema.
5. Apply `02-api-grants.sql` and `03-worker-grants.sql` as the production
   migration owner. Apply `04-verify-isolation.sql` as administrator.
6. Attempt actual cross-database logins with each pilot and production runtime
   and migration identity. Verify all six attempts fail. Test the production
   API and worker privilege profiles within `governance_prod`, including RLS
   denials and absence of owner/DDL privileges. Recheck pilot health and backup.

Keep the production database unused until the separate application, backup and
recovery gates pass. Before migrations, rollback is deletion of the unused new
database and roles after reviewing provider state. After migrations, preserve a
reviewable snapshot and remove only production grants/services in a separate
change; never roll back by changing pilot grants or deleting the pilot database.
Any production data requires an independently reviewed recovery/cutover plan.

## Separate backup and restore acceptance

Production needs its own encryption key, B2 bucket or isolated destination and
credentials, prefix, completion marker, journal inventory, timer and alerts.
Capture the production database with all production worker journals under a
coordinated writer pause, authenticate the uploaded archive, and confirm an
independent restore key can discover and download it. Restore to an isolated
replacement database on a **different cluster** while the source cluster is
treated as unavailable. Review rows, receipt proofs, revoked access and every
worker journal before any service activation. Measure recovery point and time.
The successful pilot same-cluster B2 drill is evidence for the pilot only.

Current backup/recovery implementation explicitly rejects `prod`; production
backup support and the replacement-cluster drill remain release blockers.

## Production app and identity blockers

- Separate DigitalOcean application instance, private managed database access,
  pinned artifact, TLS hostnames, protected secrets, service roles, readiness,
  deployment and rollback are not provisioned yet. The indicative starting
  Droplet is London Basic 2 vCPU/4 GiB/80 GiB at $24/month; this is a budget
  estimate, not capacity acceptance.
- WorkOS Production was inspected separately from pilot Staging. It has no
  callback or logout URLs, webhook endpoint or application key; password sign-in
  and MFA are off. A control-plane change returned `FORBIDDEN` for the connected
  admin role on 11 October. The owner must enable Production access/billing or
  grant the necessary permission before settings can be applied. Keep sign-up
  and customer traffic closed until MFA, hosted sign-in, callbacks, webhook
  verification and recovery are accepted.
- The runtime startup and several storage/recovery modules still deliberately
  reject `prod`. Adding a production migration path does not lift those gates.
- The production evidence chain, contract, wallet custody and funding are
  undecided. Base Sepolia test receipts do not satisfy production acceptance.

No production database, app, WorkOS configuration, backup or restore has been
activated by this review.
