## Product direction

The first user-facing product is a governance workspace for agent/model
inventories, decision and outcome reporting, policy/configuration monitoring,
alerts and investigation. Receipt, batching, Base settlement and verification
components provide the integrity layer beneath those workflows. The blockchain
is the independently queryable timestamped commitment layer; it is not the
customer telemetry database or analytics engine. The dashboard and API connect
the public anchor to structured private records, selected evidence, permissions
and the audit trail retained under the customer's access policy.

The dashboard must distinguish three questions:

1. **Was an anchor transaction included?** Read the transaction receipt, verify
   the expected contract event and check the receipt's block hash against the
   current canonical block.
2. **Is this receipt included in that batch?** Recompute the batch Merkle root
   from the retained manifest and verify the receipt-specific inclusion proof.
3. **What does the submitted record support?** Inspect authorized structured
   governance records and receipt commitments. Source prompts, documents and
   raw telemetry stay in customer systems; the customer can verify them locally
   against the commitment without uploading them to AIChain.

These are separate checks. A batch event proves that a publisher anchored a
root, count and schema. The event does not contain the receipt IDs, manifest,
source evidence, model execution trace or proof openings. A successful anchor
must never be presented as proof that an AI outcome is correct or safe.

## Shipped first increment: public testnet explorer

`website/app/explorer/` provides a read-only Base Sepolia explorer. Its same-
Base Sepolia endpoints with sequential failover. The dashboard shows recent `ReceiptBatchAnchoredV2`
events and accepts a transaction hash to check the receipt, chain ID, anchor
contract/event, canonical block hash and current confirmation count.

This page contains no wallet connection, signing, raw evidence, API key or
write operation. It is testnet-only and its activity scan is deliberately
bounded to the most recent 1,000 blocks to fit the public RPC range limit. A
transaction can be verified even when it is outside that recent activity window
by entering its hash. Until the index query API is connected, the public
activity table remains a short recent-block view.

Live route smoke on 2026-09-24 confirmed that the public API can still verify a
known older acceptance transaction as a canonical inclusion, while the recent
activity endpoint returned zero anchors in its latest 1,000-block window. This
confirms the indexer-history integration is needed for useful archive browsing;
the current route already handles recent RPC reads and transaction lookup.

The explorer also has an alpha, browser-local receipt proof check. A user first
verifies the anchor transaction, then selects a manifest and enters a receipt
ID. The browser bounds input size, validates the manifest, recomputes its
Ethereum Keccak Merkle root, checks its batch ID/root/publisher/count/schema
against the canonical event, builds the receipt-specific sibling proof and
verifies it against the on-chain root. The manifest is never sent to the
explorer API. The UI does not label testnet confirmation counts as finality or
claim that membership validates receipt contents or AI safety.

## Delivery phases

### A. Read-only explorer — current increment

- Chain connection health, Base Sepolia chain ID and latest block.
- Recent publisher-scoped batch events from the deployed anchor contract,
  within the public RPC's 1,000-block query limit.
- Transaction-hash lookup with successful receipt, event and current canonical
  block checks.
- Explicit distinction between on-chain anchor verification and private
  receipt-membership verification.
- No wallet, user content, raw evidence or transaction submission.

### B. Receipt and proof viewer — alpha implementation

- **Implemented alpha slice:** browser-local manifest selection and receipt-ID
  membership verification, bound to the transaction, canonical block and V2
  event checked by the explorer. Input is limited to 2 MB and 10,000 receipts.
- **Implemented and live-tested alpha slice:** Base Sepolia V2 batch event
  worker scans bounded 1,000-block ranges, persists each completed range,
  checks range-end hashes, detects reorgs, and rebuilds derived state from the
  deployed contract's creation block. It uses sequential RPC failover and an
  exclusive writer lock. A deployment-to-head catch-up found nine batch events;
  a second process resumed from its saved cursor. See the live evidence in the
  [indexer record](../completed-stages/phase-2d-durable-avr-indexer.md).
- **Deployed:** the durable worker runs on the VPS and follows Base Sepolia
  from anchor-contract creation, with persistent block-hash checkpoints,
  reorganisation rebuilds and bounded RPC failover. It is a separate read-only
  systemd unit; the existing synthetic ingress remains independent.
- **Remaining:** observe a sustained run and move to a dedicated RPC provider
  for dependable operation; provide a private manifest source; expose the
  derived index through an authenticated query API; connect the website to
  indexed history and receipt lookup.
- Associate canonical events with manifests using `(chainId, contract,
  batchId, batchRoot, publisher)`; reject mismatches and retain orphaned
  manifests outside the active index.
- Search by receipt ID, transaction hash, batch ID and permitted business
  metadata. Return the signed receipt and Merkle proof only under the
  authorised disclosure policy.
- Verify each presented receipt's signature, context, commitments, batch
  inclusion proof and anchor transaction; return a machine-readable result
  with individual check outcomes and evidence provenance.
- Support customer export bundles that an external auditor can verify without
  an Orvessian account or API.

### C. Customer workspace and API

- Tenant identity, roles, scoped API keys, audit logs and least-privilege
  project separation.
- Submission API with idempotency, quotas, priority tiers, queue-age limits and
  transparent acceptance/anchoring state.
- Private evidence storage separate from the public chain; retention, deletion,
  key rotation and disclosure controls designed before real customer data.
- Customer dashboard showing accepted, queued, batched, submitted,
  confirmed, delayed, rejected and recoverable records as distinct states.
- Gas sponsorship and relayer use behind a reviewed service boundary, daily
  spend limits, durable shared state, retry rules and a tested emergency stop.

### D. Safety evidence and operational monitoring

- Display signed monitor events, policy versions, alert dispositions and
  authorised interventions as evidence records, not as a guarantee of safety.
- Preserve who/what/when/why fields, integrity commitments and correction or
  supersession links.
- Separate source-monitor health and action taken from the fact that a record
  was anchored. The ledger records supplied evidence; it cannot observe the AI
  system or prove that the evidence is complete.
- Add API, queue, batch-age, anchor-confirmation, RPC, gas-budget and recovery
  views only when those production signals exist and have defined ownership.

## Data and verification boundaries

| Data or check | Public chain | Customer store/index | Dashboard behavior |
|---|---|---|---|
| Batch ID, root, publisher, count, schema, transaction/block references | Yes | Indexed for search/recovery | Show as public anchor facts |
| Receipt ID and receipt-to-batch association | Normally no | Manifest/index, access-controlled | Reveal only to authorised users; export when permitted |
| Signed receipt and evidence descriptors | Commitment only | Tenant-scoped receipt store | Show claims and integrity-check results with provenance |
| Source prompts, inputs, outputs and documents | No | Customer's own systems only; AIChain stores references/commitments | AIChain never accepts or stores source bytes; customer-controlled retrieval is a separate future integration |
| Monitor alerts and intervention narrative | Only if explicitly committed | Signed evidence and policy record | Show origin, time, policy version and action owner separately |
| Inclusion/finality | Event and block metadata | Confirmation observations/checkpoints | State current canonicality and confirmation policy, not generic “final” |

## Release gates before customer records

- Independent review of receipt signing, event parsing, canonicality/reorg
  handling, access control and tenant isolation.
- Authenticated customer API and production-grade durable storage with tested
  backup, restore, retention and deletion.
- Operated indexer with independent RPC observation/fallback, lag alerts,
  checkpoint integrity and replay after interruption.
- Relayer/key-custody review, transaction allowlist, gas budget and emergency
  stop before any unattended submission.
- Auditor export specification and independent verifier tested by someone
  outside the authoring team.
- Privacy, security, reliability and marketing copy all agree on what the
  record can and cannot establish.
